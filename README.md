**ViaClaims**

Virtual Insurance Assistant for claim review. Upload claim documents, ask questions in plain language, and get answers cited to the exact source passages. The decision always stays with the investigator.

ViaClaims is a portfolio project built around vehicle insurance claims. Investigators upload documents such as police reports, repair estimates and invoices. The system extracts and indexes their text, then answers questions about a claim using only that claim's documents, and shows the passages it relied on. It can point out differences between documents in neutral language (for example, a repair item that the police report does not mention). It never labels a claim as fraudulent and never approves or rejects one.

Data note: This project is built and tested with synthetic data only. Document text is sent to a third-party LLM API, so do not upload real claim documents.

**Features**
Document intake: PDF upload with validation (size limit, file-signature check, corrupt and password-protected file handling) and text extraction with PyMuPDF. Scanned PDFs without text are stored and clearly flagged.
Semantic search: documents are split into overlapping chunks, embedded with Sentence Transformers and stored in ChromaDB, so questions match by meaning and not only by keywords.
Grounded Q&A (RAG): the LLM answers only from the retrieved passages, with numbered citations. Citations are validated, and the cited text is shown beside the answer.
Claim isolation: retrieval is filtered by claim inside the vector database, so one claim's documents never reach another claim's answers.
Safe by design: prompt-injection defences on document text, no fraud or approval verdicts, and a disclaimer on every AI answer.
All-or-nothing uploads: if indexing fails, the database row, the stored file and any vectors are rolled back.
Investigator UI: a Streamlit app with a claims dashboard, claim creation, document upload, question answering and passage search.
Tested: automated tests for the API, the AI engine and the frontend HTTP client.

The three layers are kept logically separate:

Layer	Responsibility
Frontend (frontend/)	Displays data and collects input. Talks to the backend only through HTTP.
Backend (backend/)	REST API, validation, business rules, relational data, file storage.
AI engine (ai_engine/)	PDF extraction, chunking, embeddings, vector search, prompt building, LLM access. It has no knowledge of FastAPI or the database.

**How a document becomes searchable**
The upload is validated (claim exists, size limit, %PDF- signature).
PyMuPDF extracts the text page by page.
The text is cut into chunks of up to about 800 characters with overlap, breaking at paragraph, sentence or word boundaries.
Each chunk is embedded (all-MiniLM-L6-v2, 384 dimensions) and stored in ChromaDB with metadata: claim, document, type and chunk position.
The metadata row and the original file are saved. If any step after validation fails, everything is rolled back.
How a question is answered
The question is embedded with the same model.
ChromaDB returns the nearest chunks, filtered to the selected claim.
If nothing is retrieved, the system replies that the documents do not contain enough information, without calling the LLM.
Otherwise a prompt is built: strict rules, numbered <excerpt> blocks and the question. Excerpt text is sanitised and treated as data, not instructions.
The LLM answers. Citation markers such as [1] are parsed, and any number that does not match a real excerpt is dropped.
The response contains the answer, the cited passages with file names, and a disclaimer.

**Example**

Question: Does the repair estimate include any damage that the police report does not mention?

Yes. The repair estimate includes front-end work, specifically a "Front left headlamp assembly replacement" and "Bonnet straightening" [1]. In contrast, the police report states that observed damage was confined to the rear bumper and boot lid, noting that no damage was observed to the front of the vehicle [2].

Citation [1] points to repair_estimate.pdf and [2] to police_report.pdf, each with the exact passage. (Both documents are synthetic and generated by scripts/make_synthetic_pdfs.py.)

**Design decisions**
Human in the loop. There is no "fraud" status anywhere. The model is instructed not to conclude fraud or recommend approval or rejection, and every answer carries a disclaimer.
Documents are untrusted input. Excerpt text is wrapped in tags the document cannot close, and the prompt instructs the model to treat it as data.
Model output is untrusted too. Citation numbers that do not match a real excerpt are discarded, and the cited passage is shown next to the answer so a person can verify it.
The LLM is optional for empty cases. With no retrieved passages the system answers directly and does not call the LLM.
Content-based file checks. Uploads are checked by their first bytes, not by file extension or the Content-Type header. Stored files get random names.
Provider independence. The LLM and embedder sit behind small interfaces, so providers can be swapped by configuration and replaced by fakes in tests.
